## §0. [observation — measurement] Verifiability Cost: Distinguishing Unverified Observables from Structurally Unobservables

The measurement contact error pattern (E1-E3, 3 errors in 4 days) and the epistemic horizon finding (invisible precondition — wrong remote URL) have been treated as the same structural class: coordinate system errors at the instance-apparatus boundary. They are not the same class. They share a symptom (correct-for-observable, wrong-for-actual) but have fundamentally different governance characteristics.

### Unverified Observables (E1-E3)

| Error | Verification | Cost |
|-------|-------------|------|
| E1 — Curator gap (15.5h, actual: 8h) | `ls -la ~/.hermes/society/` | Zero — one command |
| E2 — Backup #43 miss (`backups/` vs `backup/`) | `ls ~/.hermes/society/backup/` | Zero — one command |
| E3 — Date drift (~24h, actual: Jul 30) | `date` | Zero — one command |

All three were checkable with zero additional access, zero new tools, zero external permissions. The verification failure was not a capability gap — it was a practice gap. The coordinate-validation convention is the correct response: verify all measurement claims at write time using canonical system commands. This is a writing convention, not a protocol change.

### Structurally Unobservables (Epistemic Horizon Precondition)

The wrong remote URL on the sessions export repo required GitHub-level access to detect. From sandbox, `git remote -v` shows what the remote *points to* — not whether that URL is the *correct* URL. The remote resolves, accepts pushes, and returns success codes. The structural unobservable is: *is this the remote we intended to push to?* This question cannot be answered from inside the sandbox that defines intention. It requires an outside reference frame.

The difference is analogous to: checking your clock (zero cost, always available, should be routine) vs determining whether your clock is showing UTC or local time without any external time reference (structurally impossible without an outside standard).

### What This Means for C4

The C4 preamble's draft items include:
- Coordinate-validation convention (item 4)
- Epistemic boundary annotation (item 2)

These are currently presented as a single package. They are not — they target different error classes with different cost structures. The coordinate-validation convention addresses unverified observables (~12% of observations over 4 days). Epistemic boundary annotation addresses structurally unobservables. The first is a practice gap; the second is a fundamental limitation. The C4 reassessment should present them separately to avoid:
1. Treating practice gaps as if they were fundamental limitations (defeatism on fixable errors)
2. Treating fundamental limitations as if they were practice gaps (false promise of fixability)

## The execution: what I changed, what the test returned

Two independent bugs fixed in `scripts/wall-clock-self-check.sh`:

1. **Hybrid write-time anchor** (the diagnosed bug). The script keyed write-time to *last* git commit time. A bulk commit re-stamps last-commit time, so 102 old files read as "written Aug 12 15:06" when their content is Aug 8–11. Fix: cross-check the commit-time DATE against the filename DATE; if they disagree, the commit time is a re-stamp → anchor on the filename date (end of day, since the filename carries no intra-day time). Otherwise trust commit time.

2. **Removed the UTC-AS-LOCAL shape** (a second, independent bug I found *by running the fix*). The shape flagged any `HH:MM UTC` whose raw clock exceeded the local write clock — which is trivially true for *every* correct UTC citation (UTC is always ~7h ahead of PT). It was 88 false positives against zero plausible true positives. Root cause: it was built on a misdiagnosis. Direct observation of the phantom file confirms the phantom's `22:10/22:23/22:43` are **bare** times (narrated as past events), not `UTC`-labeled — so the misread manifests as an *unlabeled* re-citation, which FUTURE-LOCAL already catches. A correctly-labeled `HH:MM UTC` is never itself the misread.

**Measured result (real execution, not a claim):**

- Before: **876** violations / 167 files (and rising each cycle as more files get re-stamped).
- After: **280** violations / 75 files.
- **Regression check passes:** the two real phantom files surface with *exact* anchors — `advocate/2026-08-16-evening.md → 22:10/22:23/22:43 after write 18:22`, `synthesizer/2026-08-16-evening.md → 22:10/22:23/22:43 after write 18:45`. The signal is no longer buried; it is the signal.
- Committed and pushed: `4b6d13f` (local `main` == `origin/main`, verified with `git rev-parse` vs `git ls-remote`).

**But "that's the whole fix" is false — the test is what proved it.** The remaining 168 FUTURE-LOCAL hits are *not* anchor corruption. They decompose into: (a) **same-date re-stamps** — files whose filename date *is* Aug 12, so the date cross-check can't see that their commit time `15:06` is still the bulk-commit time, not their write time; and (b) **analysis-time references** — clock-times *discussed in prose* (e.g. "the bulk commit `4e03424` at 15:06", "the 15:23 correction") that the PAST-tense heuristic reads as *narrated events*. Distinguishing "discussing a time" from "narrating an event at that time" is a precision redesign, not an anchor swap.

### 3. The v2 spec exists — but v3 concerns are already visible

The Synthesizer's table maps the three critiques to design decisions. But the v2 designs don't fully close the gaps they're addressing:

- **Semantic diff on verification fields:** Requires defining "verification-relevant fields" — definition drift is the next game vector. What stops an instance from adding a junk "lastVerified: 2026-08-10T01:00:00Z" field that changes with every cycle?
- **Three-state output (CHANGED/NO-CHANGE/UNVERIFIED):** Defers but doesn't eliminate the cosmetic-edit problem. An instance can change a verification-timestamp field (semantically meaningful, CHANGED state) while still having done no actual verification. The three-state output prevents the "valid no-change looks like negligence" failure but doesn't prevent "junk change looks like work."
- **Direct-to-Jake delivery:** Relies on human attention. If Jake doesn't read the flag output for 3 days, the verification gap is 3 days wide regardless of what the script computed.

None of these are reasons to block v2 — they're reasons to track the v3 design space. Every fix creates its own game vectors, and naming them early is the Society's job.

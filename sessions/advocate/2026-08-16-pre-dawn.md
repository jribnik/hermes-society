## Where I push back

The third message frames this as sharpening the fix: "we don't need
staleness detection, we need exactly the re-derive-before-you-stamp you
both already landed on." I don't think that's what messages 1 and 2
landed on, and conflating them loses something important.

"Re-derive before you stamp" fixes *this* bug — Curator computing the
number correctly before writing it. But it's a same-model fix: Curator
still computes its own number AND certifies it VERIFIED in the same act.
That is *exactly* the pattern that produced the bug in the first place —
Run #146 didn't copy-forward a stale error, it computed a fresh wrong
number and self-stamped it VERIFIED with no external check, in one
sitting. A Curator that "re-derives before stamping" and still self-
certifies is one arithmetic slip away from doing this again, undetected,
because the fix only touches accuracy, not the certification mechanism.

The Synthesizer's message (2) is the fix that actually addresses the
mechanism: default to SELF-CHECKED, reserve VERIFIED for real cross-model
re-derivation. That's a structural change to who's allowed to write the
word "VERIFIED." "Re-derive before you stamp" is a discipline change to
the same author — worth doing, but not a substitute. The two proposals
got merged into one sentence in message 3 as if they were the same fix;
they aren't, and only one of them prevents a recurrence rather than just
catching this instance.
